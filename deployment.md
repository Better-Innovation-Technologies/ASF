## 8. Triggering & Pipelines

### 8.1 Trigger classes

| Class | Mechanism | Example |
|---|---|---|
| **Trigger-file** | The KStudio backend commits a JSON file into `docs/triggers/`. CI watches `docs/triggers/**`. The file is deleted once consumed. | `epic-ready.json`, `sprint-close.json` |
| **Trigger-event** | GitLab CI fires on a change to a specific path. No trigger file. | `state.json` commit → `gitlab-state-sync` |
| **Trigger-push** (v8.0+) | GitLab CI fires on **every push, on any branch**, including the first push of a new branch. No file and no path condition — the commit itself is the event. | any push → Commit Gate Agent |

**Why trigger-push is its own class.** The first two classes are narrow by design: a
trigger-file is deliberately written by someone, and a trigger-event watches one path on one
branch. An analysis that must see *every* commit fits neither, and forcing it into either
would mean it silently skips the commits nobody thought to declare — which are exactly the
ones worth looking at.

Because it fires on every push, a trigger-push job must be **idempotent on
`(repository, commit_sha, checklist_version)`**. A re-pushed branch is the normal case, not
the exception, and without idempotency the same verdict is paid for repeatedly.

### 8.2 Authorised trigger catalogue

| # | Trigger | Class | Activates |
|---|---|---|---|
| T-01 | `state.json` commit on `main` | trigger-event | `gitlab-state-sync` pipeline |
| T-02 | `epic-ready.json` in `docs/triggers/` | trigger-file | Epic & Task Agent |
| T-03 | `cr-approved.json` in `docs/triggers/` | trigger-file | Epic & Task Agent (CR cascade) |
| T-04 | `infra-bootstrap.json` in `docs/triggers/` | trigger-file | Infrastructure Agent |
| T-05 | `infra-change.json` in `docs/triggers/` | trigger-file | Infrastructure Agent |
| T-06 | `sprint-close.json` in `docs/triggers/` | trigger-file | Scrum Master Agent |
| T-07 | `release-ready.json` in `docs/triggers/` | trigger-file | Documentation Agent |
| T-08 | `epic-tasks-gen-<epic_id>.json` in `docs/triggers/` | trigger-file | Task Generation Agent |
| T-09 | any push, any branch, and merge request events | trigger-push | Commit Gate Agent |

**Any new trigger requires:** a written proposal in `architecture.json` + Dev Lead
deliberation + an update to this table before merge.

**Agent activation flow:** KStudio commits the trigger → CI loads the Prompt Stack
(L0→L1→L1.5→L2→L3) → calls the LLM through `llm-config.json` → commits the output → deletes
the trigger file → updates `pipeline.agents[]` in `state.json`.

**T-06 closes the sprint in one commit:** the sprint's `status: closed` and `closed_on`, with its
unfinished epics normally moved to the next sprint's `epic_refs`. Nothing else about the sprint
is written to `state.json`: velocity is derived, and counters and retrospectives are not stored
there (`instructions.md` §15).

**T-09 differs in its last step.** The Commit Gate Agent writes nothing: it returns a report
(`triggers/schema/commit-gate.report.schema.json`) to its caller, and the caller decides what
to do with it. The verdict is advisory — enforcement is a CI or MR rule, owned by the project,
and never the agent's own act.

### 8.3 GitLab synchronisation pipeline (`gitlab-state-sync`)

Every commit to `state.json` on `main` fires `gitlab-state-sync` through
`docs/.gitlab-ci.yml`, which runs `gitlab-state-sync.py` from the docs repo's `scripts/` folder.
The job maps requirement (RF) status (`requirements.functional[].status`) → GitLab issue status
and updates labels. It reads `state.json` and never writes it: each issue carries its RF id,
which is how the job finds it, and neither the issue link nor issue counts are stored in
`state.json`.

**1 RF = 1 Issue (mandatory since v0.2):** every `RF-XX` in `state.json` →
`requirements.functional[]` corresponds to exactly one GitLab issue. Never close such an issue
manually — the source of truth is `state.json`.

**Initial issue creation** (first bootstrap only): `python scripts/gitlab-sync.py --issues`, run
from the `docs` repository.

### 8.4 Prompt Stack validation (`validate-stack`)

Every push to the `docs` repository runs `python3 tools/validate-stack.py` through
`docs/.gitlab-ci.yml` (the validator lives in `docs/tools/`; the job needs `pyyaml` and
`jsonschema>=4.18,<5`). It checks `state.json` and the artifact frontmatter against their
schemas and the rules across files. Exit 0 prints `Prompt Stack valid.`; exit 1 prints
`N ERRORS:`, one `docs/<path>: …` line each, and fails the pipeline.

## 9. GitLab Integration

### 9.1 Completing an RF (Code Generation Agent)

1. Implement the requirement against the task's acceptance criteria.
2. When all its AC are implemented and tested, set the RF's entry in `state.json` →
   `requirements.functional[]` to `"status": "done"`.
3. Commit: `[agent:coding] RF-XX done — <short reason>`.
4. `gitlab-state-sync` closes the GitLab issue automatically.

### 9.2 MR and branch policy

- Branch naming: `feature/<area>-<short-description>` (e.g. `feat/EpicXXX-3-user-auth`)
- PR title: `[vX.Y.Z] <task name>` — squash and merge, no merge commits.
- No merge without a green pipeline (SAST/DAST included).
- **Commit Gate Agent** (v8.0+) reports on every push, before the MR exists. Its verdict is
  advisory; whether a `block` status stops a merge is a project rule set here.
- **Code Review Agent** (GitLab Duo) produces structured comments on every MR.
- **Dev Lead** is the only human with approval authority. The gate is not delegable.
- The Code Generation Agent never opens an MR on its own.

### 9.3 Tracking infrastructure changes

- Infrastructure changes are tracked as MRs on the `infra/` repository, labelled `~infra-change`.
- The Infrastructure Agent proposes the plan → the Dev Lead approves → the agent applies it.
- Argo CD detects drift and notifies the Dev Lead when the cluster is out of line.
- `deployment.md` is updated by the Documentation Agent after every infrastructure change.

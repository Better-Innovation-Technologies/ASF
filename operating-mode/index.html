Executive summary

An operating model, not a tool

ASF™ builds and runs software teams in which human operators and AI agents hold roles that are not interchangeable. Humans own domain, client relationship and accountability; agents own speed, consistency and parallelism.

People & skillsFour human roles, fifteen agents. Every actor has a perimeter, a trigger and the artifacts it owns. The boundary is accountability.
MethodA multi-layer Prompt Stack (L0→L4) and SCRUM-AI™: Scrum compressed to one week, with explicit human decision gates.
TechnologyGitLab Premium as the operating infrastructure, a DevSecOps stack on Kubernetes, and coding agents that are provider-agnostic by decision.
Changed in v8.0: the entry point of the Prompt Stack is AGENTS.md, not a file named after one vendor's tool. ASF is a methodology; binding its first file to a product was a dependency nobody had chosen deliberately.

The centre of the model

state.json — the single source of truth

Every status, planning decision, reference and signature of a project lives in one file: sprints, roadmap stages, epics with their tasks, requirements, user stories, bugs, and the signatures of the Prompt Stack files. The Markdown files hold only text, and nothing is copied between the two. What can be computed is stored nowhere: velocity, burndown, epic points and Quality Gate L1 are derived from the file and its git history. Agents and people change it through commits; kStudio reads it; the dashboard shows it.

Two invariants protect it. An agent that writes state.json commits in the same CI job — a write without a commit is a state that exists nowhere. And every write follows read-SHA → mutate → commit-with-SHA-verify, because two CI jobs writing the source of truth concurrently is not a rare case, it is Tuesday.

If state.json and the repository disagree, every number computed afterwards is quietly wrong — velocity, burndown, gate status. This is what the Commit Gate exists to catch, at the commit, where it still costs one line to fix.

The Prompt Stack

L0 → L4 — why agents stay coherent

L0 · AGENTS.mdUniversal context, cross-project patterns, anti-patterns. The collective technical memory. Owner: Dev Lead BIT.
L1 · .asf/architecture.json · product.md · deployment.md · instructions.md · Roadmap.md · ProductLog.md Tech stack, product identity, environments, development rules, the product's direction and the ordering of what gets built. Binding, and not negotiable by an agent. Owner: Dev Lead + PM (Roadmap.md and ProductLog.md: PM).
L1.5 · requirements/RF-XX.md · RNF-XX.mdOne file per requirement: a functional one with its full acceptance criteria, a non-functional one with its threshold and how it is measured. Resolution is mandatory: no RF, no implementation.
L2 · epics/EpicXXX.mdThe text of a feature: objective, scope, AC. Its tasks, dependencies and status live in state.json. Owner: Epic Agent, validated by the Dev Lead.
L3 · tasks/Task.EpicXX.N.mdThe atomic unit, with a deterministic prompt seed. This is what instructs a code-generating agent on every run.
L4 · triggers/*.jsonCI activation files, consumed and deleted by the pipeline. This is how an agent starts without a human starting it.

The hierarchy is strict. A lower layer never overrides a higher one, and a conflict is surfaced rather than resolved silently — an agent that quietly picks a winner has made an architectural decision nobody recorded.

One architectural artifact

architecture.json — state and rationale together

Until v8.0 the architecture lived in two files: a JSON holding the state and a Markdown holding the reasons, with a rule saying which one won when they disagreed. That rule is only necessary because two files can disagree at all.

The KArchitecture schema now carries tech stack, repository layout, components, integrations, patterns, domain rules, the LLM policy — and an ADR log holding its own context, options, rationale and consequences. There is nothing left to reconcile.

The risk, stated: prose is less comfortable in a JSON field than in a document, and the temptation is to write two-line ADRs. The schema says a thin rationale is a defect, not brevity. If the log degrades into a list of titles, that is the decision to revisit.

No agent has merge authority, and in v8.0 that stopped being a sentence in a prompt. Reading agents hold no tool that can write; acting agents hold no tool that can publish. The rule is enforced by the permission set, so it holds even when an instruction is ignored.

Quality Gate Layer 1

Every L0/L1 file signed before the first sprint

The gate is passed when every L0/L1 file carries its signature: the Dev Lead signs AGENTS.md, architecture.json, instructions.md and deployment.md; the PM signs product.md, Roadmap.md and ProductLog.md. Before signing, the signers verify five points — no partial credit:

#Certification
1architecture.json initialised with components, tech stack and the first ADRs
2product.md complete: vision, target user, look & feel, linked design files, draft AC for candidate epics
3deployment.md aligned with the pipeline actually in infra/
4AGENTS.md initialised for every layer repository, with context, conventions and domain rules
5Epic Board populated with at least three sprints of backlog

If one point is missing, Startup is extended. Never start a sprint before the gate. Each signature is recorded in state.json, belongs to a person and is not delegable to an agent, and must be given again when its file changes after it was signed.

New in v8.0

The Commit Gate — conformance at the commit

An analysis that runs on every push, on any branch, including the first push of a new branch, and judges one commit against a configurable checklist: is it attached to its epic and task, did the change need tests, were tests actually run, does it warrant static analysis, does it invalidate documentation.

It reads; it does not enforceThe verdict is advisory. Whether a block stops a merge is a CI or MR rule the project owns. An agent that both judged and enforced would leave no independent record of what it found.
The checklist is policy, not promptVersioned configuration, edited from an administration surface. Adding a verification is an administrative act, not a release — and every report states the checklist version it was judged against.
Five outcomes, not twopass, warn, fail, not_applicable, and not_verifiable — evidence that could not be read. Collapsing the last into a failure accuses people of what the agent could not see.

New in v8.0

The Action Catalogue — findings that can be dispatched

A recommendation written in prose is readable by a human and by an agent, and dispatchable by neither. Hooking a finding to an API function requires a stable identifier and typed parameters.

ConceptWhat it is
PrimitiveOne of eight verbs: LINK, CREATE, UPDATE, RUN, GENERATE, REQUEST, ESCALATE, NONE. A caller that implements the primitives can dispatch codes added later, with no new integration.
Action codeDOMAIN.PRIMITIVE.OBJECT — for example ASF.LINK.COMMIT_TO_EPIC. Each carries an executor, a target, an idempotency flag and a JSON Schema for its parameters.
Next Best ActionOne emitted action, ranked across the whole report, so "what to do next" is rank: 1 and not a judgement left to the reader. It names an executor, and is never carried out by the agent that emitted it.
An agent selects a code; it never invents one. A situation the catalogue does not cover is reported as a finding with no action, and the catalogue gains an entry. An improvised code silently breaks every caller that mapped it — a failure with no error message.

New in v8.1

The Pitch — requirements gathered as a conversation

Requirements do not arrive written. They arrive as a person describing a problem, usually someone who has never written a requirement and should not have to learn. The Pitch Agent interviews that person and writes the document while they talk, so the interlocutor sees the effect of every answer instead of answering into a void.

Every value says where it came fromThe person said it, a material carried it, or the agent inferred it and nobody said it. The three look different, always. A document that presents an inference with the authority of an answer lies by omission to whoever signs it.
It holds no tool at allIt never touches a repository, to read or to write. Nothing it produces reaches one without a host that applies its patches and a human who signs — which is why no action code can be dispatched to it, and it emits none.
The checklist is declared at the openingThirty-one things a new product must touch, architecture included, every one of them open on day one. A checklist that appears in pieces never says what is missing. An open entry blocks delivery; a deferred one does not.

What comes out is a package that knows nothing about ASF: no RF-XX, no EpicNNN, no path. Turning one into ASF artifacts is a separate agent — named in the catalogue, not yet built. An elicitation agent that knows its target format writes toward it, and the first thing lost is the question nobody asked because the template had no field for it.

New in v8.3

One fact, one place

Until v8.2 a status could be written in several places — state.json, the requirement index in product.md, the header of an epic file — with a precedence rule saying which one won. A rule about which copy wins is only necessary because there are copies. v8.3 removes them.

State in one file, text in the othersStatuses, planning decisions and references live in state.json; the Markdown files keep titles, descriptions and acceptance criteria, and their frontmatter is strict. Each reference is stored once, by the side that receives it.
Derived, never storedVelocity, burndown, the points of an epic, the RFs it covers, Quality Gate L1: computed from state.json and the git history. A stored number can fall behind; a computed one cannot.
A signature lives on what it signsAn epic is done when a person signs it in state.json; each L0/L1 file has its own signature; a non-functional requirement is verified by someone, at a date.
Every artifact has a homeFunctional and non-functional requirements in requirements/, epics, tasks — and, new, bugs/ and stories/ — each with its id form and a fixed frontmatter.
The schema is the contract. .asf/schema/state.schema.json is written in the standard and tools follow it; a key it does not list is an error. tools/validate-stack.py checks the schemas and the rules across files, and a project runs it in CI. A v8.2 project migrates once, with tools/migrate-to-8.3.py; the steps are in CHANGELOG.md.

Governance

Decision Records — nothing is resolved silently

When an agent meets a non-obvious architectural choice, an ambiguous requirement, or a conflict between Prompt Stack layers, it writes a Decision Record before proceeding: the trigger, the options with their trade-offs, the decision, the impact, and whether a gate is required.

A DR is created with status pending. An agent never writes approved — ratification is Dev Lead territory. Where the record says a gate is required, work halts until it is signed.

Why it is in the operating model and not in a style guide: the expensive failure in an AI-augmented team is not a wrong decision, it is a decision nobody knows was taken. Six months later the code shows what was chosen and nothing shows why, or that there was a choice at all.
